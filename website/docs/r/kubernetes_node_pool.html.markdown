# Resource: nscale_kubernetes_node_pool

Manages the workers for a [`nscale_kubernetes_cluster`](kubernetes_cluster.html). NKS models node pools as a separate
top-level resource, so a pool references its cluster by ID rather than being a field on it. A cluster with no node
pools has nowhere to schedule work.

`provisioning_mode` selects the capacity source: `compute` draws on-demand instances of a given flavor, `reservation`
draws from a [`nscale_reservation`](reservation.html). Supplying the wrong block for the mode, or both, fails at plan
time.

!> **Editing `taints` or `labels` replaces every node in a compute pool.** NKS does not reconcile either onto running
workers, so a change rolls the pool. Terraform shows this as an ordinary in-place update, because that is what it is at
the API level — see [Rolling a pool](#rolling-a-pool) for how the roll behaves and how PodDisruptionBudgets affect it.

~> **A reservation pool is close to immutable.** Only `description` and `tags` update in place. `replicas`, `taints` and
`labels` all force replacement, because the placement backing the pool never rolls and the change could not otherwise
take effect. Scaling a reservation pool is a rebuild, not a scale.

~> **`project_id`, `organization_id` and `region_id` are read-only.** They are inherited via the cluster, which derives
them from its network. Setting any of them is an error.

-> **The NKS endpoint must be configured.** Set `nks_service_api_endpoint` on the provider, or the
`NSCALE_NKS_SERVICE_API_ENDPOINT` environment variable, before using this resource.

## Example Usage

```hcl
resource "nscale_kubernetes_node_pool" "workers" {
  name              = "workers"
  cluster_id        = nscale_kubernetes_cluster.main.id
  provisioning_mode = "compute"
  replicas          = 3

  compute = {
    flavor_id = data.nscale_instance_flavor.worker.id
  }

  # Editing either of these later rolls the pool's workers, one at a time.
  taints = [{
    key    = "workload"
    value  = "general"
    effect = "PreferNoSchedule"
  }]

  labels = {
    tier = "standard"
  }
}

resource "nscale_kubernetes_node_pool" "gpu" {
  name              = "gpu"
  cluster_id        = nscale_kubernetes_cluster.main.id
  provisioning_mode = "reservation"
  replicas          = 2

  reservation = {
    reservation_id = nscale_reservation.gpu.id
  }

  # This pool is reservation-backed, so editing taints, labels or replicas
  # replaces it rather than updating it in place.
  taints = [{
    key    = "nvidia.com/gpu"
    value  = "true"
    effect = "NoSchedule"
  }]
}
```

## Schema

### Required

- `cluster_id` (String) The identifier of the NKS cluster the node pool provides workers for. The pool's project, organization and region are all inherited from the cluster. Immutable: a pool cannot move between clusters, so changing this forces a new node pool to be created.
- `name` (String) The name of the node pool. Immutable: changing this forces a new node pool to be created.
- `provisioning_mode` (String) Where the pool's worker capacity comes from. `compute` draws on a compute flavor and requires the `compute` block; `reservation` draws on reserved capacity and requires the `reservation` block. The mode also decides how much of the pool can be changed in place — see `replicas`. Immutable: there is no in-place migration between modes, so changing this forces a new node pool to be created.
- `replicas` (Number) The number of workers the pool should run. On a `compute` pool this is an in-place scale, and `0` is valid — a pool scaled to zero keeps its configuration but runs no workers. On a `reservation` pool it forces replacement: a placement cannot be resized, so changing this releases and re-claims the reservation's capacity rather than scaling.

### Optional

- `compute` (Attributes) Compute-backed worker capacity. Required when `provisioning_mode` is `compute`, and must be omitted otherwise. (see [below for nested schema](#nestedatt--compute))

- `reservation` (Attributes) Reservation-backed worker capacity. Required when `provisioning_mode` is `reservation`, and must be omitted otherwise. (see [below for nested schema](#nestedatt--reservation))

## Rolling a pool

Changing `taints` or `labels` on a compute pool changes the template its workers are built from, so every existing
worker is replaced. NKS applies both during node registration and does not reconcile them onto running nodes
afterwards, which is why a change has to recycle the fleet to take effect at all.

The replacement is a controlled rolling update:

* One extra node at a time — the pool adds a worker before removing one, and never drops below `replicas` ready
  workers.
* Each outgoing worker is **cordoned and drained** through the Kubernetes Eviction API, so **PodDisruptionBudgets are
  honoured**.
* Because it proceeds one node at a time, a roll takes roughly `replicas` times the cost of building and draining a
  single worker. Raise `timeouts.update` for a large pool.

Watch `up_to_date_replicas` to follow a roll: it drops as workers are replaced and returns to `replicas` when every
node runs the new template.

!> **A PodDisruptionBudget that can never be satisfied blocks the roll indefinitely.** There is no drain timeout, so
the pool stops mid-rollout and `terraform apply` runs out its own timeout. The same applies to destroying a pool, and
to destroying a cluster — both drain their workers. A timeout here does not mean the roll failed: it is still in
progress. Fix the disruption budget and apply again.

Reservation pools never roll. Any change that would need one forces replacement instead.

## Async behaviour

Creates, updates and deletes are asynchronous, and Terraform waits for each. The waiter is the same one the cluster
uses. An apply returns once `status.observedGeneration` has caught up with the pool's spec generation **and**
`provisioning_status` is `provisioned`. Until the generation catches up, the API is still reporting status for the
previous spec.

~> **Health does not gate the apply.** NKS defines convergence as the generation being observed plus
`provisioning_status` reaching `provisioned`, and documents health as an independent signal that "does not determine
convergence". A pool can therefore report `degraded` — or `error` — on a successful apply; one worker failing its
Kubernetes node conditions is enough to degrade an otherwise converged pool. Read `health_status` and
`ready_replicas` to judge whether the workers are actually carrying load.

A successful apply therefore means the pool's template has converged — `up_to_date_replicas` equals `replicas` — but
not necessarily that every worker is Ready, and `ready_replicas` can legitimately lag. `current_replicas` is how many
workers exist, `ready_replicas` how many can take work, and `up_to_date_replicas` how many run the current pool
template. Watch the last one to follow a roll.

A pool can be created or added at any time, including before its cluster is `provisioned` — the API does not require
the cluster to be ready first.

## Timeouts

The `timeouts` block supports:

* `create` - (Default `30m`)
* `update` - (Default `60m`)
* `delete` - (Default `60m`)

Creating a pool is a set of workers joining an existing cluster, and is quicker than building a control plane. `update`
and `delete` get longer because both walk the pool one worker at a time: an update may roll every worker, and a delete
drains every worker on the way out.

## Notes

~> **Updates are a full replacement.** NKS exposes `PUT`, not `PATCH`, so the provider rebuilds the whole spec from your
configuration on every update. Removing an argument clears it rather than leaving it alone. This is also what makes
scaling safe: a `replicas` change re-sends your `taints` and `labels` unchanged rather than dropping them.

* Deleting a cluster removes its node pools. Terraform destroys pools first, because they depend on `cluster_id`.
* `taints` is a list and round-trips in the order the API returns. `labels` is a map, with at most 64 entries.
* A node pool has no platform release argument of its own — it inherits the cluster's, and reports it as
  `applied_platform_release_id`. To move a pool onto a newer release, upgrade the cluster's `platform_release_id`.
* A reservation-backed pool fails to provision if the reservation has no capacity available.
* `name`, `cluster_id`, `provisioning_mode`, `compute.flavor_id` and `reservation.reservation_id` are all immutable at
  the API, which rejects a change outright. The provider plans a replacement so the change is achievable rather than
  failing at apply.
