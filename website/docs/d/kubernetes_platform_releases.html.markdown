# Data Source: nscale_kubernetes_platform_releases

Lists Nscale Kubernetes Service (NKS) platform releases — the versioned Kubernetes platforms an
[`nscale_kubernetes_cluster`](../r/kubernetes_cluster.html) can run.

Use this instead of hardcoding a `platform_release_id`: release IDs change as the catalogue moves, and a configuration
that pins one by hand goes stale the moment that release is deprecated.

-> **The NKS endpoint must be configured.** NKS has no default endpoint baked into the provider yet. Set
`nks_service_api_endpoint` on the provider, or the `NSCALE_NKS_SERVICE_API_ENDPOINT` environment variable, before
using this data source.

## Example Usage

Select the newest release eligible for a new cluster:

```hcl
data "nscale_kubernetes_platform_releases" "eligible" {
  region_id  = nscale_network.main.region_id
  deprecated = false
  withdrawn  = false
}

resource "nscale_kubernetes_cluster" "main" {
  name                = "production"
  network_id          = nscale_network.main.id
  platform_release_id = data.nscale_kubernetes_platform_releases.eligible.releases[0].id
}
```

Pin to a specific Kubernetes minor version rather than to whatever is newest:

```hcl
data "nscale_kubernetes_platform_releases" "all" {
  region_id    = nscale_network.main.region_id
  architecture = "x86_64"
  withdrawn    = false
}

locals {
  release_1_33 = one([
    for release in data.nscale_kubernetes_platform_releases.all.releases :
    release if startswith(release.kubernetes_version, "v1.33.")
  ])
}
```

## Schema

### Optional

- `architecture` (String) Only return releases supporting this CPU architecture. One of `x86_64` or `aarch64`.
- `deprecated` (Boolean) Filter by deprecation state. Set to `false` to return only releases that are still current. Omit to return both.
- `organization_id` (String) Only return releases usable by this organization. Defaults to the organization configured on the provider.
- `prerelease` (Boolean) Filter by prerelease state. Omit to return both prerelease and non-prerelease releases.
- `region_id` (String) Only return releases available in this region.
- `withdrawn` (Boolean) Filter by withdrawal state. Set to `false` to exclude releases operators have withdrawn. Omit to return both.

- `releases` (Attributes List) The matching platform releases, in the order returned by the API. (see [below for nested schema](#nestedatt--releases))

## Selecting a release

The API returns releases in catalogue order, so `releases[0]` is the newest match. Which filters you want depends on
what you are doing:

* **Creating a cluster** — filter `deprecated = false` and `withdrawn = false`. These are the releases that are
  genuinely current.
* **Upgrading a cluster** — filter `withdrawn = false` only. You may need to re-state a release your cluster is
  already on which has since been deprecated, and excluding deprecated releases would make that configuration
  un-appliable. Withdrawn releases are never selectable.
* **Reading the whole catalogue** — omit the filters. Each release carries `deprecated`, `withdrawn` and `prerelease`
  as attributes, so you can filter in HCL instead.

An omitted filter is not sent to the API at all, which is different from filtering on `false`. `deprecated = false`
returns only current releases; omitting `deprecated` returns both current and deprecated ones.

Prefer reading `eligible_upgrade_target_ids` on an existing cluster when planning an upgrade — the API computes
eligibility for that specific cluster, which is stricter than anything you can derive from the catalogue alone.

## Notes

* A release is selectable in a region only when that region appears in its `available_region_ids`, and it is usable by
  your organization only when that organization appears in `usable_organization_ids`. Filtering by `region_id` and
  `organization_id` applies both server-side.
* `organization_id` defaults to the organization configured on the provider, so most configurations do not need to set
  it.
* `deprecated` means existing clusters should upgrade away from a release. It is an operator decision and can be
  reversed. `withdrawn` is stronger: operators have pulled the release from selection, and `withdrawal_reason` and
  `withdrawal_message` explain why.
* `prerelease` releases are selectable and are offered as upgrade targets, but they are superseded — and so deprecated
  — as soon as a newer release appears. Avoid them in production configurations.
* Selecting a release that is withdrawn, or unavailable in your cluster's region, fails at apply time with HTTP 422.
